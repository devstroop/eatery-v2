## Bottom line

The foundation is real and the working tree is materially better than the
commit: the app builds, `native check` passes, the order insert now
succeeds, and the working tree runs **28/28 tests**, including 12
in-memory database tests. The committed `HEAD` still has the order-write
defect and only 13 tests, so the two states must not be confused.

The remaining blockers are **identity and money**, not the write path:

1. ~~**Login never checks the employee's stored role.**~~ FIXED
   2026-10-21: the sign-in query is scoped to the session's role and the
   returned row is checked against it.
2. ~~**The provisional salt is still accepted.**~~ FIXED 2026-10-21: the
   salt is a three-state lifecycle, the sign-in waits for the database to
   confirm it, and the setup writes it with the operator's hash.
3. **PIN security is weak.** Fast SHA-256 over four digits, no per-user
   salt, no lockout, no masked entry. Still open.
4. **Clock-shaped order IDs still collide** and `ON CONFLICT(id)` can
   merge orders.
5. **Money is still subtotal-only.** Tax, discount and payment are not
   implemented; an order can complete unpaid.
6. **First-run setup exists but is not trustworthy.** The currency
   symbol field writes the code, the submit button is never disabled.
   The salt race it carried is closed.

Everything else — no printing, no sync, no reports, no packaging — is a
product gap on top of those blockers. The payment/confirmation flow is
partial and has its own defects (B-033/B-035). The documentation set is
unusually candid but has stale counts and overstatements (18 findings).

## What is healthy

- Model / Msg / update separation is consistent; the setup flow uses the
  same channel rather than a shortcut.
- The order write, nullable FKs and company ownership are fixed and
  covered by the in-memory suite.
- A first-run setup now creates a company, an operator, the installation
  salt and a usable starter menu/floor, in one transaction.
- The sign-in checks the employee's stored role, and the salt is only
  used once the database has confirmed it.
- Screen ordinals are append-only, documented as a contract, and a test
  now pins the gated ordinals against the enum; every mounted screen is
  built by the suite.
- The schema is broad, `STRICT`, integer-money and millisecond-time; the
  migration lock and `native check` are real.
- The documentation has a clear status vocabulary, honest ADRs and a good
  open-questions page.
- CI and helper scripts exist; the pinning rationale is sound.

## What the docs should say after this pass

- The order flow works in the **working tree**, not in committed `HEAD`.
- CI exists but its smoke does not exercise a sale.
- Tests: 15 authored headless + 12 in-memory DB + 1
  generated = 25 in the working tree; the committed tree is 13.
- The RBAC matrix test is tautological; do not cite it as proof.
- Salted SHA-256 is a storage improvement, not adequate PIN security.
- First-run setup exists but has currency/validation gaps.

## Limitations

- The engine's foreign-key, journal and drain semantics were not inspected
  in the SDK source; G-025 records the unknown.
- Linux/Windows builds and the CI smoke were not run; only macOS was
  exercised.
- The working tree changed during the review; findings describe the
  snapshot, and four defects (B-001, B-004, B-005, B-030) were fixed mid-review.
- No penetration test, fuzzing, load test or hardware test was performed.

## Recommended sequence

1. Fix B-002/B-003 and add login/role/salt tests; then B-027.
2. Commit the DB harness and the order-write fix, and make CI run it.
3. Replace the order ID scheme (B-006) and guard status transitions
   (B-008); then tax/payment (B-014).
4. Fix session/navigation state (B-009/B-010/B-011), the orders list
   (B-012), and the setup gaps (B-031/B-032).
5. Work through the screen gaps in product order; do not add enum entries
   without templates and coverage.
6. Correct the documentation counts/claims and add link/claim checks.
