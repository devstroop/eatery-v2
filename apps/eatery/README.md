# Eatery v2 — the app

A restaurant operating system in one native binary: **point of sale,
kitchen display, customer display and back office**, written in Zig on the
[Native SDK](https://native-sdk.dev).

The app follows the SDK's app model exactly:

```
Model   ── what is true              (src/core/model.zig)
Msg     ── what happened             (src/core/msg.zig)
update  ── what is true now          (src/core/update.zig)
markup  ── what the operator sees    (src/app.native, src/screens/*.native)
```

The markup never changes state: it binds model values and dispatches
messages. Every state change happens in `update`. The world is reached
only through the effects channel, so `update` stays a pure function of
(model, message) and the whole app can be driven headlessly in a test.

> This README describes the app as it is in the tree. The repository root
> README covers the rewrite as a whole; the architecture notes live in
> [`docs/`](../../docs/README.md).

## Running it

### Requirements

| Tool | Version | Why |
|---|---|---|
| Zig | **0.16.0** | The SDK pins it. |
| Node | **24+** | The relational-schema generator is TypeScript. |
| Native SDK CLI | **v0.11.0** | `native dev / test / check / build / automate / db / package` |

The CLI binary is `native`. It is not on the PATH in this checkout, so
the commands below assume the toolchain is already installed and on PATH.

### Everyday commands

Run them from the app directory.

```sh
cd apps/eatery

native dev            # debug build, run, markup hot reload on src/app.native
native test           # the headless test suite
native check          # validate the markup, the manifest and app.json
native build          # ReleaseFast binary in zig-out/bin/
```

```sh
native db new-migration add_promotions   # append src/schema/0011_add_promotions.sql
native db status                         # source schema version vs installed version
native db reset --yes                    # delete the development app.db
```

```sh
native automate wait                        # wait for the running app
native automate snapshot                    # dump the widget tree
native automate assert 'gpu_nonblank=true'  # assert on the snapshot
```

`native db new-migration` writes the numbered file and the leading comment
("Append-only SQLite migration. Use STRICT tables so generated types stay
honest. This version may never be edited after it is shipped."). The
engine applies the migrations when the database opens; `migrations.lock.json`
records the source version (currently `10`) and a hash per migration.

`native check` validates the markup and the manifest, and it prepares the
schema with real SQLite: a non-`STRICT` table or a broken foreign key fails
the check. It does not open the app's live database; that happens at
runtime.

### Live smoke test

```sh
native dev                 # in one terminal
native automate snapshot   # in another
```

### What works end to end

1. On a fresh database, setup creates the company, an Admin PIN and a starter
   menu; then choose Admin → PIN → dashboard.
2. Dashboard → POS → search and filter → add to cart → set the order type
   → place the order. The working tree writes `orders.updated_at`, so this
   now succeeds; the committed `HEAD` still omits it (B-001).
3. Orders → advance the status → `orders.status` plus a row in
   `order_status_history`.
4. Choose Kitchen → board → advance the tickets.
5. The title bar's **Theme** button toggles light and dark.
6. The setup screen creates a starter menu and six tables; the floor board
   renders them.
7. Choose Waiter → tables → menu → cart → the order joins the table's open
   order.
8. Choose Display → the customer board shows the order cards.

### The shell

One window, one view:

| Field | Value |
|---|---|
| label / title | `main` / `Eatery` |
| size | 1280 × 800, minimum 960 × 600 |
| restore policy | `center_on_primary` |
| view | `main-canvas`, kind `gpu_surface`, fill `true` |
| GPU backend | `metal`, `bgra8_unorm`, present mode `timer`, `opaque`, `srgb`, vsync on |

`main.zig` builds the same window in Zig (`shell_windows`, `shell_views`)
and passes it as the `UiApp` scene. The two have drifted: the manifest
declares the minimum size and the restore policy, and the Zig shell config
does not set them. See the known gaps.

`security.navigation.allowed_origins` is `zero://app` and `zero://inline`;
external links open in the system browser. The web engine is `system`, and
the CEF directory is configured but not installed.

## Known gaps

### Flows that do not work

1. **A fresh install cannot sign in.** There is no setup flow: no company
   row and no employee, so the login query matches nothing.
2. **The waiter role lands on an empty pane.** The role and the rail
   exist; there are no waiter templates.
3. **The display role lands on an empty pane.** The screen is an enum
   entry with no template.
4. **Order confirmation has no template.** Placing an order navigates to a
   screen that renders nothing.
5. **Most rail destinations render nothing.** The catalog, people and
   system sections have no templates.
6. **There is no way to pay for an order.** The `payment` table exists and
   nothing writes to it.
7. **No receipt and no kitchen ticket.** `printer` and `auto_print` exist;
   `tools/print-sidecar/` is empty.
8. **A second device sees nothing.** `op_log`, `device` and `sync_state`
   exist; no operation is ever written to `op_log` and
   `tools/sync-sidecar/` is empty.
9. **Customers are never loaded.** `repos.loadAll` calls seven loaders
   and `loadCustomers` is not one of them.

### Defects in the current tree

| Defect | Where | Effect |
|---|---|---|
| The provisional salt is installed and `pin_salt_len` set before the database confirms the salt; `submit_login` checks only that the salt is non-empty, not `salt_is_provisional` | `src/main.zig`, `src/core/update.zig` | a fast sign-in can hash against a salt that is then replaced |
| The order id is the wall clock in milliseconds and the order number is the wall clock in seconds | `src/core/update.zig` | two orders in the same second collide on `orders.order_no`, which is `UNIQUE` |
| The shell gates compare hard-coded screen ordinals | `src/app.native` | inserting a screen in the enum silently remaps the shell |
| The orders badge says "open" but binds `order_count`, which counts every non-voided order including completed ones | `src/screens/screen-orders.native` | a misleading number |
| `auth.equal` is tested but the login path does not use it | `src/data/auth.zig` | the constant-time compare is not protecting the sign-in |
| The manifest declares a 960 × 600 minimum and a restore policy that the Zig shell config does not set | `app.json`, `src/main.zig` | `native dev` can open a window the manifest does not allow |
| `busy` is set on writes, never on reads | `src/core/update.zig` | no loading state on a slow query |
| `view_unbound` lists `pending_screen`, which is not a field | `src/core/model.zig` | a stale lint entry |
| There is no screen-coverage test | `src/tests.zig` | a blank pane is invisible to the suite |
| CI exists but its smoke only asserts a non-blank canvas | `.github/workflows/ci.yml` | a broken sale path still passes |
| Order insert omitted `orders.updated_at` (`NOT NULL`) | `src/data/repos.zig` (`saveOrder`) | every order write failed; fixed in the working tree |
| Login ignores `employee.role` | `src/core/update.zig` (`login_sql`) | any PIN can open Admin |
| Table/customer ids were `0`, not `NULL` | `src/core/update.zig` (`placeOrder`) | FK failure or orphan references; fixed in the working tree |
| Company strings pointed into page scratch | `src/data/repos.zig` (`decodeCompany`) | title bar/currency could dangle; fixed in the working tree |
| PIN is a fast SHA-256 over four digits, with no lockout or masking | `src/data/auth.zig`, `src/screens/screen-login.native` | offline brute force and shoulder-surfing |
| Status advance is not conditional | `src/core/update.zig` (`advance_order`) | double taps duplicate history |
| No `build.zig` in the app directory | app root | fine while the CLI manages it; blocks linking a C library until `native eject` |

### Not covered by the tests

Login against a real database, the order write and read-back, every decoder
except the generic page reader, every screen template except the role
picker and the login, the node budget, the theme tokens, the timer, the
error arms, the salt lifecycle, and both sidecars.

## How to add a screen

1. **Append the screen** to the `Screen` enum in `src/core/navigation.zig`.
   The enum order is a contract: `screen_index` is what the markup
   compares against, so append and never reorder. Give it a `title()`, and
   a `nav_section()` if it belongs in a rail.
2. **Decide the permissions.** Add the screen to `rbac.allows` for every
   role that may open it, and to `rbac.home` if it is a role's landing
   screen. The matrix test is meant to walk every role against every screen; the
current one is tautological (see the audit).
3. **Add the message** to the `Msg` union in `src/core/msg.zig` if the
   screen dispatches one. If no markup dispatches it, list it in
   `view_unbound`.
4. **Add the data** if the screen needs it: the SQL as a named constant
   in `src/data/repos.zig`, a `load*` function, a decode function, and a
   dataset plus a bump buffer in `src/core/model.zig`. Derived values are
   methods on `Model`, never stored fields.
5. **Write the template** at `src/screens/screen-<name>.native`, opening
   with `<template name="screen-<name>">`.
6. **Register it** in `src/app_sources.zig` (the embedded import closure)
   and add the matching `<import src="screens/screen-<name>.native"/>` to
   `src/app.native`. A file the markup imports but the closure does not
   list fails at the import site.
7. **Mount it** in the shell: add an
   `<if test="{screen_index == N}"><use template="screen-<name>"/></if>`
   gate inside the content pane of `src/app.native`, where N is the new
   enum index.
8. **Handle the message** in `src/core/update.zig`, and navigate with
   `go(model, screen)` so the permission check runs.
9. **Test it.** Add a case to `src/tests.zig` that builds the tree and
   asserts on a text node, the way the role-picker test does.
10. **Run `native check` and `native test`.**
